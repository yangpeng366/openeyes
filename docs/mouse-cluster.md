# 鼠标集群：多个 Agent 同桌协作

- 方向：鼠标集群（mouse cluster）——多个 AI Agent 各自拥有一个可见光标，同屏并行干活，尽量不打扰用户
- 分两层：视觉层（满屏多个光标在动，看得出谁在动）、系统层（每个 Agent 独立输入通道、后台并行操作）
- 配套文档：`docs/isolation-policy.md`（隔离阶梯与升级判定）、`docs/architecture.md`（分层与后端降级链）、`docs/capability-contract.md`（工具与投递契约）
- 实机核查日期：2026-11-09

## 0. 这份文档解决什么

用户要的是「鼠标集群」：一桌人肉 Agent，每个都有一根看得见的自己的光标，能同时在屏幕上干活，而用户那根物理鼠标尽量不被抢。

这个诉求里其实有两件被捆在一起的事：

1. **看得见**——多个 Agent 同时在屏幕上动，用户能分辨谁在动（视觉层）；
2. **不打扰**——Agent 干活时尽量不夺走用户的指针与注意力（系统层）。

两件事的技术难度不在一个量级。第一件是画几个图标；第二件撞的是 Windows 的硬约束：**一个会话只有一个前台窗口、一根系统指针、一块用户真正在看的桌面**。本仓前七步（动作账本、投递阶梯与抢前台预算、跨进程租约、Agent 光标、注意力预算、冲突预测调度、隔离判定与在场接线）做的都是第二件事，以及为它配套的第一件事。

本文回答四组问题：

- **哪些活适合**、哪些不适合（§2）；
- **除了「同屏看 Agent 干活」，还能用在哪儿**，各自的收益与代价（§3）；
- **「不干扰用户」有哪几种形态**，机制、代价、本机可行性（§4）；
- **技术选型怎么站**：无障碍树派还是像素/输入注入派（§5）。

最后给出现状盘点（§1）与可独立验收的小步计划（§6）。

与 `docs/isolation-policy.md` 的分工：那一份讲**什么时候必须离开共享桌面**（判定与升级条件），本文讲**整个方向的形状**（做什么、为什么做、做到什么程度算够）。凡涉及阈值与判定口径，本文只引用，不重定义。

## 1. 现状盘点

### 1.1 已落地

| 能力 | 文件 | 对外契约 |
| --- | --- | --- |
| 身份与前景预算 | `openeyes/agent/profile.py` | `AgentProfile`（身份、模式、优先级、是否许抢前台）、`FocusBudget`（抢前台次数的滑动窗口，`refused` 记账）、`color_for`（身份 → 稳定配色） |
| 动作账本 | `openeyes/agent/ledger.py` | `ActionLedger` / `record_action`：记投递路径（semantic / message / pixel / foreground / none）、是否动了物理输入、是否被验证过 |
| 跨进程输入租约 | `openeyes/agent/lease.py` | `InteractionLease`：Windows 上是按 SID 的排他 `CreateFileW`，进程死则锁自解；等待有上限，拿不到给结构化码 `LEASE_TIMEOUT` |
| Agent 光标 | `openeyes/agent/overlay.py` | `CursorOverlay` / `render_cursor`：**一张画在桌面上的画**——不驱动指针、不抢前台 |
| 注意力预算 | `openeyes/agent/attention.py` | `AttentionBudget`（attention budget）：每分钟可打扰用户几次；`take(False)` 既不消耗额度也不计 `refused` |
| 冲突预测调度 | `openeyes/agent/scheduler.py` | `Scheduler` / `Conflict`：同目标争用，同优先级不抢占，严格更高优先级才抢占并留一条冲突记录 |
| 隔离判定 | `openeyes/agent/isolation.py` | `IsolationConfig` / `IsolationVerdict` / `evaluate_isolation`：三条触发——真并行 → `vm`、语义路径大面积失效率 → `session`、打扰预算反复耗尽 → `session` |
| 在场接线 | `openeyes/agent/presence.py` | `AgentPresence`：决策信号 → 注意力预算 → Agent 光标三者接通 |
| 决策信号 | `openeyes/decision/action.py`、`openeyes/decision/router.py` | `Action.needs_attention` 只在 `FLAG_FOR_REVIEW` 这一档为真，其余档位一律为假 |

未落地的部分见 §7，**不要把「判定代码存在」当成「隔离环境可用」**。

### 1.2 本机硬事实（实测，勿改写口径）

- 操作系统：**Windows 11 家庭版 Insider Preview，build 26340**；
- 显示：**AMD 独显，2240x1400**；
- 在册虚拟显示器驱动两个：**OrayIddDriver（向日葵）**、**Todesk Virtual Display Adapter**；
- **`WS_EX_LAYERED` 分层窗口在本机根本不会被 DWM 合成到屏幕上**：
  - `UpdateLayeredWindow` 的 `ULW_ALPHA`（三种调用顺序）与 `ULW_COLORKEY` 全部无效；
  - `SetLayeredWindowAttributes` 的 `LWA_ALPHA` 与 `LWA_COLORKEY` 全部无效；
  - 取景侧三种方式结论一致：GDI `BitBlt|CAPTUREBLT`、普通 `ImageGrab`、DXGI 桌面复制；
  - 而**普通（非分层）顶层窗口合成完全正常**：100x60 实测 **6000/6000 像素全中**。

（口径小差异：同一 build 在 `docs/isolation-policy.md` §4.1 记为 Windows 10 Home，OS 版本口径待统一，见 §7。）

### 1.3 由此得出的实现约束

**Agent 光标必须用「非分层顶层窗口 + 窗口区域（`SetWindowRgn`）」实现，不能依赖分层窗口。**

这条约束不是偏好，是本机的实测结论：分层窗口在本机不参与 DWM 合成，无论用哪一种分层调用、无论从哪一种取景方式去看，都看不见它。而普通顶层窗口的合成完全正常，100x60 的窗口在截图里 6000 个像素全中——所以「画一张不规则形状的画」这件事，用普通窗口 + 窗口区域照样做得到。

这条约束同时是「虚拟显示 / 后台桌面 2」路线的现实依据：换到虚拟显示器或独立会话里，光标仍然是窗口，仍然要被 DWM 合成，分层窗口在那条路上同样不可靠。换环境不改变渲染前提，所以光标的实现路线必须现在就定死，不能指望「先按分层写，等换了环境再改」。

本文只描述 Agent 光标的**对外契约**——它是一张画，不驱动指针、不抢前台——不依赖 `overlay.py` 的内部实现。

### 1.4 一条贯穿全篇的纪律

`docs/isolation-policy.md` §5 已列了一串「不要做什么」，本文再加一条总的：

> **没有实测数字就不要写「已隔离」。**

本方向最容易出现的失败，不是做不出来，而是**做了一半就宣称做成了**：说「Agent 在后台跑不打扰用户」，其实它只是很少抢前台；说「支持并行」，其实只是两个 Agent 交替动手。文档里的每一处定性描述，都应当能追到一个数字或一个可复现的判定。

## 2. 适用场景：哪些活适合，哪些不适合

先说硬约束，因为所有判断都由它推出：**一个 Windows 会话里只有一个前台窗口、一根系统指针、一块用户真正在看的桌面。** 多个 Agent 同桌，能并行的是「感知」与「决策」，动手的部分永远要排队（`docs/isolation-policy.md` §4.2）。

### 2.1 适合

| 场景 | 为什么适合 | 关键前提 |
| --- | --- | --- |
| 只读巡检、状态核对、留证 | 走 UIA / CDP 拿结构化元素，不碰指针就能读到界面状态 | 目标应用有可用无障碍树或 DOM |
| 有原生接口的自动化（CLI、URL scheme、UIA Invoke 模式） | 语义路径（semantic path）直接命中，不抢前台也不动指针 | 控件暴露可调用的操作模式 |
| 低频复核型任务 | 只在 `FLAG_FOR_REVIEW` 档位才要人看一眼，注意力预算（attention budget）把「看一眼」限量 | 复核频次低于每分钟预算 |
| 并行**观察**、串行**动手** | 多个 Agent 同时盯不同窗口、同时推理，动手时由租约（lease）与调度器排队 | 同目标争用能被 `Scheduler` 判定 |
| 把「多光标」本身当演示素材 | 视觉层本就是给人看的，调试与讲解 Agent 行为时它反而是主角 | 光标实现不抢焦点（§1.3） |

### 2.2 不适合

| 场景 | 为什么不适合 | 该怎么办 |
| --- | --- | --- |
| 真·同时动手（两个 Agent 必须同一秒点不同位置） | 物理上不存在：只有一个前台窗口与一根系统指针 | 换隔离环境（§4），或把任务改写为串行 |
| 图形化编辑器、游戏、画图、拖拽类操作 | 几乎只能走像素 + 拖拽，会持续抢前台与指针 | 判定为 `session` 级，换独立会话 |
| canvas / 自绘控件 / 远端桌面 | 语义路径大面积失效，失效率高 | 走 `vision` 解析层，并接受「像素最后」的代价 |
| 需要用户同步盯着看的协作 | 人的注意力只有一份，多 Agent 抢同一个人 | 降为后台运行 + 事后汇总 |
| 不可逆且无确认的高危操作（付款、删除、发布） | 注意力预算只能**挡住一部分**打扰，挡不住误操作本身 | 保留人工确认闸门，不拿预算当安全机制 |

一句话概括：**适合「多个 Agent 各自用语义路径干活，用户偶尔瞥一眼」；不适合「多个 Agent 同时用鼠标在同一个窗口里乱点」。**

## 3. 更多可能的使用与优化场景

「同屏看 Agent 干活」只是这个方向最容易想到的用法。下面几项分别给出机制、**收益**与**代价**，以及它们各自把需求推向哪一层隔离（层级定义见 `docs/isolation-policy.md` §1）。

### 3.1 录制演示素材 / 教学回放

- **机制**：让 Agent 走一遍完整流程并录屏，产出教程视频、回归演示、复现材料；Agent 光标可以入镜，也可以按 `needs_attention` 决定是否出镜。
- **收益**：演示材料的边际成本从「人反复手演」降到「跑脚本」；Agent 的每一步都有动作账本（`ActionLedger`）与截图证据链，失败回合也能复盘。
- **代价**：Agent 的路径有随机性，录出来不一定是「最好看」的一遍，往往要重跑若干次挑一条；录制过程本身会持续抢前台，用户在场时反而被打扰；素材的「可讲解性」仍需人工过一遍。
- **推向**：L0 / L1；无人值守录制另配 §3.3 的预算放开策略。

### 3.2 批量表单 / 巡检的并行化

- **机制**：把一批表单或一批待巡检目标分给多个 Agent，各干各的。
- **收益（真实的）**：墙钟时间可以压缩；但要分清是**真并行**还是**伪并行**。同一台桌面、同一根系统指针上，多个 Agent 动手只能排队，收益来自「分片后少冲突、少重试」，而不是同时点。`evaluate_isolation` 的 `needs_parallel` + `concurrent_writers` 就是用来把这两者分开计的。
- **代价**：并行收益必须靠隔离环境兑现（每片一个独立会话或一台 VM；单靠多一块虚拟屏不解决输入互斥，见 §4.2），环境成本、维护成本、失败时的取证复杂度都上去了；分片逻辑本身有 bug 时，错误会被并行放大。
- **推向**：真并行 → L4（VM）；伪并行 → L0/L1 就够。**

### 3.3 人不在时的无人值守

- **机制**：用户离开时把注意力预算放开（`per_minute` 调大或换成「只在收尾时汇报」），让 Agent 连着跑；期间所有 `FLAG_FOR_REVIEW` 的复核项攒起来，用户回来一次性过。
- **收益**：把「人在场的时间」换成「机器的时间」；夜间批处理、巡检、批量录入的墙钟收益是数量级的。
- **代价**：「不打扰用户」这个前提此时已经不存在了，剩下的约束只有租约与调度；而**没有人看着的时候，打错也没有第二双眼睛**——所以证据链（截图 + 动作账本 + 复核项清单）必须先于无人值守跑起来，否则出错等于没出错。
- **推向**：L0 / L1 为主；若必须物理点击且无人值守，按 §4 走独立会话。

### 3.4 跨应用编排

- **机制**：一个「决策者」Agent 拆任务，多个「执行者」Agent 分别在浏览器、编辑器、终端、IM 里推进，每步把结论交回决策者。
- **收益**：不同应用各干各的，感知与决策真能并行；这是共享桌面上最接近「并行」的一种用法，因为冲突主要发生在「谁抢前台」而不是「谁在点」。
- **代价**：仍然共享一根系统指针与一个前台，**抢前台预算（`FocusBudget`）是瓶颈而不是并发度**；任一执行者掉进像素路径，其他人都得排队等它把前台还回来；跨应用的上下文传递要自己设计（本仓暂未提供）。
- **推向**：L0 / L1 / L2 组合；应用间切换越频繁，抢前台越频繁，预算越容易见底。

### 3.5 把「打扰度」变成可度量的产品指标

- **机制**：动作账本已经在记 `physical_input`、`focus_stolen`、`cursor_moves`、`verified`，注意力预算在记 `refused`，隔离判定在读这三组数字。
- **收益**：对用户可以回答一个具体问题——「这套自动化每小时打扰我几次」；对自己可以回答「把语义路径命中率提上去之后，打扰少了多少」。这是本方向唯一能证明自己在变好的标尺。
- **代价**：指标要定义得诚实（`refused` 计入被保护掉的打扰，与 `physical_input` 分开记）；口径一漂移，指标就没意义了。
- **推向**：不涉及隔离，是所有层共用的度量。

### 3.6 其它可考虑的用法

- **影子模式（shadow）**：Agent 只出计划、不落地，用来评估「如果让它做，会发生什么」。`AgentProfile.mode` 已有 `MODE_SHADOW` 一档，天然适合当安全演练。
- **回归用例的并行化**：每个用例一个隔离环境，测试机之间互不抢前台——需要环境供给，本机尚不具备（§7）。
- **协作式观察**：多个 Agent 同时盯同一套界面、各自汇报发现，动手部分仍由调度器排队——这是「多光标」最有说服力的展示场景。

## 4. 「不干扰用户使用」的四种形态

「不干扰」不是一种技术，是四种机制，各自的隔离强度与代价差得很远。先给结论，再逐一说。

| 形态 | 隔离了什么 | 机制要点 | 代价 | 本机可行性 |
| --- | --- | --- | --- | --- |
| A. 桌面 2 / 独立会话 | 前台窗口（有自己的前台可抢） | `CreateDesktop` 或另起用户会话 | 另起环境的成本；用户看不见，回报要另设通道；跨桌面投递受权限与 LUID 约束 | **未实现**，只有判定代码 |
| B. 虚拟显示屏幕 | 渲染与占屏 | 在册虚拟显示器驱动（向日葵 / Todesk）提供虚拟输出 | 只解决「看得见」，不解决输入互斥 | 驱动在册，**活动输出未验证** |
| C. 虚拟鼠标键盘 | （名义上）输入通道 | 软件层 HID 设备 / RawInput 自绘 | 汇入同一根系统指针与同一前台队列 | **不能作为并行方案** |
| D. 同桌面 + 语义优先 + 预算 | 指针与注意力的**用量** | `invoke→message→pixel` 阶梯、租约、注意力预算、冲突调度 | 无法真并行；语义失效时仍会抢前台 | **已落地，本机可跑** |


### 4.1 A：背景运行在「桌面 2」（第二桌面 / 独立会话）

- **机制**：给 Agent 一个属于自己的桌面（`CreateDesktop`）或另一个用户会话。Agent 抢的是它自己那个前台，不是用户的；用户的窗口继续是用户的前台。
- **代价**：另起会话/桌面的成本（内存、启动、生命周期管理）；用户看不见那边发生了什么，**状态回报要另设通道**（文件、剪贴板、HTTP 回传）；跨桌面投递输入受权限与 LUID 匹配约束。
- **本机可行性**：**未实现**。本仓目前只有判定代码（`evaluate_isolation` 返回 `level='session'`），没有能起一个独立桌面并在其中驱动 GUI 的实现。按 `docs/isolation-policy.md` §4.2 的记录，桌面 2 只能藏不能并行，且跨桌面投递需要 `SE_TCB_NAME` 权限与 LUID 匹配；本机是家庭版（按同文 §4.1 的记录，RDP 默认关闭、无 Sandbox），这条路必须先做最小可行性验证（§6 步骤 8），而不是直接当成可用方案。
- **它能解决什么**：**「别打扰用户」——真的能解决**。它解决不了「真并行」：会话里仍然只有一根系统指针（`docs/isolation-policy.md` §4.2）。

### 4.2 B：虚拟显示屏幕（虚拟显示器 / 独立输出）

- **机制**：把 Agent 的桌面渲染到一块虚拟显示器上（第二块输出），用户在主屏干活，Agent 在虚拟屏干活。本机在册两个虚拟显示器驱动：**OrayIddDriver（向日葵）**、**Todesk Virtual Display Adapter**。
- **代价**：只解决「渲染与占屏」，**不解决输入互斥**——多一块屏不等于多一根指针（`docs/isolation-policy.md` §4.2 第 2 条、§5）。Agent 在虚拟屏上点的，仍是那根系统指针，仍进同一个前台队列。因此单靠虚拟显示器，「不打扰用户」的效果有限，除非配合 A 或 D。
- **本机可行性**：驱动在册，但按 `docs/isolation-policy.md` §4.1 的记录，**当前没有活动分辨率的虚拟显示器**；把它配置成活动输出并验证截图、分辨率与输入去向，属于**待验证**（§6 步骤 7）。
- **附带的渲染约束**：换了输出不等于换了渲染前提。**分层窗口在本机照样不被 DWM 合成**（§1.3），所以虚拟屏上的 Agent 光标仍然只能用非分层 + 窗口区域实现。

### 4.3 C：虚拟鼠标键盘（注入输入但不抢物理鼠标）

- **机制**：装软件层的虚拟 HID 设备，或用 RawInput 自绘一个「假指针」来区分 Agent 与用户。
- **代价**：**软件层的键鼠驱动最终仍汇入同一根系统指针与同一个前台队列**——它改变的是「事件从哪来」，不是「队列在哪」；而 RawInput 是「读」不是「造」，自绘出来的是画面，不是输入。
- **本机可行性**：**不能作为并行方案**。`docs/isolation-policy.md` §5 已明令「不要用 RawInput 多鼠标自绘冒充多根指针」。它在视觉层有用（区分谁在动），在系统层没用。

### 4.4 D：同桌面 + 注意力预算 + 语义路径优先（当前主线）

- **机制**：不换桌面，而是让共享桌面变得「可共享」：能走语义路径就不动指针（`invoke → message → pixel` 投递阶梯，`docs/capability-contract.md`）；必须动指针时用租约串行化，且抢前台的次数要记账（`FocusBudget`）；Agent 想被看见时先过注意力预算（`AttentionBudget`）；同目标争用由调度器排队或抢占（`Scheduler`）；动过的每一笔都进动作账本（`ActionLedger`）。
- **代价**：**无法真并行**——动手永远排队；语义路径大面积失效时，Agent 会退化成「打鼠标的人」，抢前台次数上升，而抢前台次数本身就是打扰（只是被限量、被记账）；一旦预算反复耗尽，按 `evaluate_isolation` 的判定就该升级环境，而不是继续硬调。
- **本机可行性**：**已落地且本机可跑**。这是唯一一条「今天就能跑、且机制闭环」的路线。
- **它不能解决什么**：真并行。`concurrent_writers` 触发的是 `vm` 级判定，不是同桌面能消化的。

### 4.5 四种形态的关系

它们不是互斥选项，而是**同一条阶梯上的不同位置**（层级定义见 `docs/isolation-policy.md` §1）：

```
D（同桌面 + 预算 + 语义优先）   ← 今天的主线，先把 L0/L1/L2 做厚
        │  语义失效率高 / 预算反复耗尽 / 需要真并行
        ▼
A（独立会话 / 桌面 2）        ← 解决「别打扰」，不解决「真并行」
        │  仍需真并行
        ▼
L4（VM）                      ← 本机无现成设施，近期不投
```

B（虚拟显示器）是**输出侧的配件**：它给 A 或 L4 提供「看得见的屏幕」，本身不构成隔离。C 是**视觉层的手段**，不构成系统层隔离。

## 5. 技术选型：无障碍树派 vs 像素 / 输入注入派

### 5.1 两派

**无障碍树派**：UIA（Windows 无障碍树）与 CDP（Chromium DOM / a11y tree）是结构化接口。它们返回控件的类型、名字、`automation_id`、状态与位置，不需要看图，也不需要算坐标。

**像素 / 输入注入派**：从截图里解析元素（vision 解析层），再用物理注入（`pixel`、`foreground`）执行。

| 维度 | 无障碍树派 | 像素 / 输入注入派 |
| --- | --- | --- |
| 覆盖率 | 受限于应用是否暴露无障碍信息 | 几乎覆盖任何屏幕上看得见的东西 |
| 可观测性 | 高：知道命中的是哪个控件、什么名字、`automation_id` 是什么 | 低：只知道坐标，不知道那是什么 |
| 对用户的打扰 | 低：语义路径不碰指针、不抢前台 | 高：正是「与人和人打架」的来源 |
| 失败模式 | 「没找到」——可能是控件没暴露，也可能压根没找过（需区分） | 「点空了」——坐标错、布局变、分辨率变，事后难解释 |
| 证据链 | 元素级：`Element[]` + 尝试轨迹 | 像素级：只能靠截图前后对比 |
| 抗变化 | 较强（控件结构比像素稳定） | 弱（分辨率、主题、布局一动就偏） |

### 5.2 口径：不是二选一，是「按顺序退让」

本仓已有的两条链子就是这两派的落地形态，且方向一致：

```
感知：uia  ->  cdp  ->  vision        （docs/architecture.md）
投递：invoke ->  message ->  pixel     （docs/capability-contract.md）
```

口径是**结构优先、像素最后**：结构化接口能用就不用像素，像素是最后手段而不是默认手段。对应到本方向，两条链子各解决一半问题——感知侧决定「看得准不准」，投递侧决定「打扰不打扰」。**鼠标集群的成败主要在投递侧**：感知可以退到像素（慢、脆，但不会打扰人），投递退到像素就意味着要动用户的指针。

### 5.3 什么时候允许下沉到像素

下沉本身要有门槛，否则「结构优先」会退化成口号：

1. **结构路径确实不可用**——要么没有语义路径（`NO_SEMANTIC_PATH`），要么够不着（`BACKGROUND_UNAVAILABLE`），并且这两个码都进了账本；
2. **打扰有账**——走像素要过租约与抢前台预算，物理输入与抢前台的次数都记在账本里，不允许「顺手点一下」；
3. **失效率要反喂给隔离判定**——`semantic_miss_rate` 上升不是「再多用几次像素」的信号，而是「该换环境」的信号。默认阈值 0.5（`IsolationConfig`），达到即触发 `session` 级升级。

### 5.4 一条容易被忽略的推论

**语义路径的命中率，就是这个方向的用户体验上限。** 命中率越高，需要动指针的动作越少，注意力预算越不容易耗尽，升级到独立会话的时机越晚——也就是说，**把感知侧做厚，等于把隔离环境的成本往后推**。这是本方向在 L0/L1/L2 上投入的回报所在。

## 6. 后续小步计划

排序原则：**每一步都能独立验收，不依赖下一步**；前面的步骤越便宜、越能减少打扰，优先级越高。步骤 1–5 是当前主线的闭环，全程在共享桌面上；步骤 6–8 是把隔离环境一条条试出来；步骤 9–10 是把度量与例外路径收口。

### 步骤 1：口径对齐（文档，一小时级）

- **做什么**：统一本机事实的写法——OS 版本（本文记 Windows 11 家庭版 Insider Preview build 26340，`docs/isolation-policy.md` §4.1 记 Windows 10 Home，build 一致）、虚拟显示器驱动的「在册」与「活动输出」之别、分层窗口在本机不参与 DWM 合成这一条。
- **验收通过**：同一台机器在两份文档里的描述不再互相矛盾；每一处定性说法都能追到一个数字或一条可复现的实测命令。

### 步骤 2：Agent 光标落到非分层 + 窗口区域 —— **已落地，剩一项实测**

- **做什么**：把 Agent 光标按 §1.3 的结论重写为非分层顶层窗口 + `SetWindowRgn`，对外契约不变（一张画，不驱动指针、不抢前台）。
- **已达成**：真实桌面上能看见光标——`examples/overlay-check.py` 实测 245 个该 Agent 颜色的像素、落点在其要求的矩形内、隐藏后归零、用户前台窗口全程未变；截图能取到它，形状与区域一致。
- **还差一项**：**点击穿透**的实机验证——点光标所在位置的底层窗口，事件真的落到那个窗口（`WM_NCHITTEST` 已答 `HTTRANSPARENT`，但要用真鼠标点一次才算数）。

### 步骤 3：双 Agent 同屏演示

- **做什么**：一个脚本拉起两个 Agent，各画各的光标（颜色由 `color_for` 按身份派生），各自移动。
- **验收通过**：屏幕上同时出现两个不同颜色的光标；用户窗口的前台焦点全程不变；动作账本里能分别看到两个 `agent_id` 的记录。

### 步骤 4：决策信号 → 注意力预算 → 光标（端到端）

- **做什么**：把 `Action.needs_attention` → `AttentionBudget.take` → `AgentPresence.announce` 串成一条真实回路，而不是三个孤立的模块。
- **验收通过**：一次 `FLAG_FOR_REVIEW` 决策会在屏幕上画出一个光标；非该档位不画；预算耗尽后不画且 `refused` 增加；`take(False)` 场景下既不画也不消耗额度。

### 步骤 5：冲突预测接进真实回路

- **做什么**：两个 Agent 抢同一个 target 时，败者拿结构化码 `TARGET_CONFLICT` 并排队，而不是各点各的。
- **验收通过**：同目标并发时**不出现并发点击**；同优先级时败者排队；严格高优先级抢占时，`conflicts()` 里留下一条记录且账本能查到这次抢占。

### 步骤 6：打扰度度量闭环

- **做什么**：把动作账本与注意力预算的数字汇总成一份可读的「这轮打扰了用户几次」报告。
- **验收通过**：跑完一个典型任务，能回答四个数——动了多少次物理输入（`physical_input`）、抢了几次前台（`focus_stolen`）、被预算拒了几次（`refused`）、多少动作被验证过（`verified`）；且这些数与账本原始条目逐条对得上。

### 步骤 7：虚拟显示器可行性验证（只验，不投）

- **做什么**：把在册的 `OrayIddDriver` 或 `Todesk Virtual Display Adapter` 配成一块活动输出，只验事实，不做产品化。
- **验收通过**：虚拟屏上能打开应用并截图取到内容；**同时确认输入仍然走同一根系统指针**（预期如此，若意外如此则成为一条重要事实）；把分辨率、色彩深度、启动方式记进文档。**若配不成，就把它写成「已排除」而不是「待优化」。**

### 步骤 8：独立会话 / 桌面 2 可行性验证（只验，不投）

- **做什么**：起一个独立桌面或另一个会话，在其中驱动一个 GUI 应用。
- **验收通过**：Agent 在那边抢的是它自己的前台，用户会话的前台窗口全程不变；跨会话的回报通过另一条通道回来（文件、HTTP 或剪贴板），不通融用户可见界面。**若权限或 LUID 匹配卡住，就把卡点写明并归入「不可行」，不要用折中方案假装成了。**

### 步骤 9：无人值守模式

- **做什么**：预算放开 + 复核项攒批 + 回来一次性过。
- **验收通过**：人不在时任务能连续跑完；人回来后拿到一份待复核清单（所有 `FLAG_FOR_REVIEW` 汇总）与对应的截图证据；整个过程的物理输入次数可查。

### 步骤 10：隔离判定接进真实回路

- **做什么**：把 `evaluate_isolation` 的读数接上真实度量（语义失效率、预算拒绝数、并发写者数），并按 `docs/isolation-policy.md` §3.3 的纪律处理降级。
- **验收通过**：需要真并行时给出 `level='vm'` 并**不假装能并行**（改为串行 + 显式排队，并记账）；恢复后按连续 N 次评估（N ≥ 3）逐级回退，且升级与降级都入账。
